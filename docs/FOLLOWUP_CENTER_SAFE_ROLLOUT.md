# مركز المتابعة — خطة إطلاق آمنة

هذا العمل تطوير معزول على فرع مستقل. بتاريخ 26 أكتوبر 2026، طُبّقت جداول مركز المتابعة ووظائفه الخمس فقط على قاعدة DXN Tahadi الرئيسية، دون إنشاء حالات فعلية أو تعديل بيانات الأعضاء الحالية. واجهة المركز لا تزال على فرع التجربة ولم تُدمج مع main.

## حالة التفعيل المرحلي

- اجتازت الجداول والدوال اختبارًا تكامليًا على قاعدة DXN Tahadi – Data API Audit، ضمن معاملة تم إلغاؤها.
- أُنشئ جدولا followup_contacts وfollowup_actions مع RLS ومنع الوصول المباشر وواجهات RPC محمية بجلسة تطبيق.
- اختبارات صلاحيات المسؤول وتسجيل العضو الجديد ومنع التكرار والحظر نجحت.
- **الخطوة المتبقية:** تجربة الواجهة على حساب مخوّل، ثم اعتماد دمجها إلى main قبل إتاحتها للجميع.

## تعديل تصنيف المستقطَبين — 27 أكتوبر 2026

- أُضيف في فرع التجربة حقل مستقل باسم «حالة المستقطَب» لا يغيّر نتيجة التواصل أو صلاحيات الحساب.
- الحالات التسع: جديد، تم التواصل، لا يمتلك واتساب، عضو في DXN، سجّل عضوية، فعّل نقاط، لا يرد نهائيًا، لا يرغب بالعمل، عمل لي حظرًا.
- «عمل لي حظرًا» يعني أن الشخص حظر مسؤول المتابعة؛ **لا** تنفّذ الواجهة أي عملية حظر.
- الاسم ورقم التواصل قابلان للبحث، ويمكن اختيار أي حالة للترشيح. يظهر وصف الحالة في كل بطاقة.
- كل تغيير فعلي يُكتب في `followup_actions` مع القيمة السابقة والجديدة، واسم المسؤول محفوظ برقم المستخدم والتوقيت والملاحظة.
- انتقال «سجّل عضوية» ينشئ بطاقة عضو جديد مرتبطة بالشخص لدى المسؤول نفسه فقط، ويتطلب رقم العضوية وتاريخ الانضمام الفعلي عند التسجيل الأول.
- حالات «لا يرد نهائيًا» و«لا يرغب بالعمل» و«عمل لي حظرًا» توقف التذكير بذلك الشخص، ولا تحذف معلوماته.
- ملف SQL الإضافي `supabase/pending-review/20261027_followup_prospect_status.sql` **للمراجعة فقط**، وليس ترحيلًا تلقائيًا.
- اجتازت التغييرات اختبارات JavaScript المركزة (17/17) واختبارات SQL في قاعدة التدقيق المعزولة داخل معاملة تم إلغاؤها `ROLLBACK`.
- **لا يُطبق SQL الجديد على الإنتاج ولا يُدمج الفرع في main قبل إكمال فحص النسخ الاحتياطي والاستعادة واختبار الواجهة.**

## لوحة إشراف القائد وإشعارات المتابعة

- تظهر «لوحة متابعة القائد» ضمن مركز المتابعة للقائد فقط، وتشمل المهتمين والأعضاء الجدد والمسؤول عن كل سجل.
- تظهر الحالة الحالية، المرحلة، وقت تسجيل البطاقة، وآخر تحديث، مع بحث وتصنيف حسب العضو المسؤول والنوع والحالة.
- يظهر في الجهة اليسرى من لوحة القائد الإجراء القادم المحدد تلقائيًا وفق المرحلة ودليل المتابعة، مع تاريخ التنفيذ ووقته ونص الرسالة، دون أن يختار السبونسر وسيلة التواصل أو يؤلف خطة متابعة يدويًا.
- تعرض بطاقة كل شخص المراحل كاملة جنبًا إلى جنب (أربع مراحل للمهتم وست مراحل للعضو الجديد)، مع رسالة مستقلة تتضمن الاسم الحقيقي وموعد محدد لكل مرحلة.
- تكون رسائل المراحل اللاحقة مرئية للمعاينة لكن زر النسخ وتسجيل النتيجة مقفلين حتى حلول الموعد واكتمال السابقة. عند الاستحقاق يُفتح زر «نسخ الرسالة» ويظهر تنبيه للمسؤول أثناء فتح الموقع.
- أسفل كل مرحلة قائمة الحالات التسع لتسجيل ردة الفعل، مع ملاحظة اختيارية. تحفظ مع رقم المرحلة والمستخدم والتوقيت عبر `followup_complete_stage` في معاملة واحدة. لا يحذف تحويل المهتم إلى عضو بياناته؛ يحمل العضو الجديد رابطًا إلى البطاقة السابقة.
- زر «تحويل إلى عضو جديد» مستقل عن قفل الرسائل: إذا سجّل المهتم فعليًا قبل حلول المرحلة القادمة يُنقل فورًا بعد إدخال رقم العضوية وتاريخ الانضمام، مع الاحتفاظ بسجل المهتم وربطه بالسجل الجديد.
- الاستثناءات: لا رسائل دون موافقة، لا متابعة بعد رفض التواصل أو الحظر، ولا إصرار على دعوة صاحب عضوية DXN قائمة إلى إعادة التسجيل. جميع رسائل المهتم الافتراضية نصية؛ لا يُفرض صوت أو فيديو دون طلب وموافقة مناسبة.
- المواعيد المستقبلية المعروضة للمرحلة غير المفعّلة «متوقعة» إلى حين إكمال ما قبلها؛ المواعيد الفعلية مصدرها قاعدة البيانات. لا إرسال آليًا لأي محتوى.
- يبدأ عدّ مراحل المتابعة عند إثبات الموافقة إذا كانت البطاقة قد أُنشئت قبلها، مع إبقاء وقت إنشاء البطاقة الأصلي للتدقيق. تُعرض الرسالة الأولى للمهتم بعد عشر دقائق على الأقل، وتُحسب بقية المواعيد من بداية التسلسل المعتمدة.
- يتيح سجل العضو الجديد قراءة إجراءات بطاقة المهتم المرتبطة به؛ لا تُحذف سجلات الأطراف السابقة.
- لبطاقة العضو الجديد ستة حقول تعريفية: الاسم، رقم العضوية، البلد، تاريخ الانضمام الحقيقي، اسم الراعي، ورقم عضوية الراعي. اسم الراعي ورقمه مأخوذان من العضو المسند إليه السجل، ويؤخذ تاريخ الانضمام المحفوظ أو تاريخ سجل أعضاء DXN عند توفره. لا يُستخدم وقت إنشاء المتابعة باعتباره تاريخ الانضمام.
- عند إضافة عضو جديد يدويًا يُطلب رقم العضوية والبلد وتاريخ الانضمام، ويحفظهما الخادم عبر دالة منفصلة `followup_add_new_member` في معاملة واحدة.
- عند إنشاء عضو حالة جديدة أو تسجيل نتيجة متابعة أو تغيير تصنيف مهتم، يُنشئ خادم قاعدة البيانات إشعارًا محفوظًا للقائد.
- يعتمد التنفيذ على جدول `app_notifications` الموجود مسبقًا، ويحفظ كل حدث جديد منفصلًا، ويتيح فتح البطاقة مباشرة من الإشعار.
- لا يصل الإشعار للأعضاء الآخرين، ولا يُرسل إشعار للقائد عن التغييرات التي يُجريها بنفسه.
- أثناء فتح الموقع، يُحدّث القائد إشعارات المتابعة دوريًا كل دقيقة تقريبًا، دون إرسال رسائل تلقائية للمستقطبين.
- ملفا `supabase/pending-review/20261027_followup_new_member_identity.sql` و`supabase/pending-review/20261027_followup_leader_notifications.sql` مسودتا مراجعة وليسا ترحيلين تلقائيين؛ ترتيبهما بعد ملف حالة المستقطَب، ثم الإشعارات.
- ملف `supabase/pending-review/20261027_followup_stage_flow.sql` مسودة مراجعة إضافية تحمي إكمال المراحل زمنيًا في الخادم؛ يُراجع بين ملف الهوية وإشعارات القائد، بعد التحقق من النسخ الاحتياطي.
- يُختبر التسلسل كاملًا على قاعدة التدقيق المعزولة داخل معاملة تُلغى، وتبقى قاعدة الإنتاج دون تغيير حتى اعتماد الاستعادة والنسخ الاحتياطي.
- تحقق محلي: 26 اختبار JavaScript ناجحًا وتدقيق بناء ملفات SQL الخمسة معًا داخل `BEGIN/ROLLBACK` على قاعدة التدقيق، دون إبقاء جداول أو تغييرات دائمة. ما زال اختبار التفاعل الحي بين المتصفح والقاعدة مطلوبًا بعد اعتماد ملفات المراجعة.

## ضوابط التشغيل

- استكمال اختبار استعادة قاعدة البيانات والتأكد من سلامة أرشيف 26 أكتوبر 2026.
- عدم الكتابة على أرشيف 24 أكتوبر لملفات Storage أو أرشيف 26 أكتوبر لقاعدة البيانات.
- أخذ نسخة جديدة مشفرة بعد اعتماد الجداول الجديدة، وتحديث دليل الاستعادة ليشملها.
- التحقق من صلاحيات كل عضو وعدم كشف بيانات المهتمين لأعضاء آخرين.
- عدم إرسال أي رسائل تسويقية آلية؛ تنبيهات النظام موجهة للعضو المسؤول فقط.
